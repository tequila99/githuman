# Жизненный цикл артефактов

Документы остаются неизменяемыми файлами. Статусы и связи меняет пакет
ChangeSet: сервер проверяет предполагаемое постсостояние, сохраняет версию
предложения и вычисляет SHA-256 digest. Перезапись содержимого не поддерживается.
На странице `/artifacts` доступен интерфейс проверки и подтверждения пакетов.
Новые ChangeSet и решения для дополнений составляет агент через MCP.

## Последовательность

1. `change_sets.propose` сохраняет `{requestId, changeSet}`. Для новой версии
   передаются `id` и `expectedVersion`. В `expectedVersions` должны быть версии
   всей области, которую показывает `POST /api/artifacts/change-sets/preview`.
2. `validations.prepare({changeSetId,version})` фиксирует manifest и возвращает
   validation ID. `validations.start({id,presetId})` запускает отдельную ACP-сессию
   выбранного серверного пресета.
3. Валидатор читает все страницы `validations.manifest({id,limit,cursor})` и все
   обязательные тексты `validations.read({id,key,offset})`. Для документа key —
   UUID. Сервер выдаёт UTF-8 блоки до 8 KiB
   с `nextOffset`, отслеживает непрерывное покрытие байтов и проверяет свежесть.
4. `validations.submit` принимает verdict `pass|conflict|incomplete`, findings
   с точными цитатами и resolutions. Digest и validatorSessionId назначает сервер.
   Неполное чтение превращает результат в `incomplete`. Необязательный `report`
   сохраняется отдельным изолированным draft; его создание не инвалидирует manifest.
   Также доступен `validations.create_report({id,body})`.
   Создание draft и связь с validation фиксируются одной транзакцией.
   При `submit` с новым отчётом в эту же транзакцию входит итог validation;
   ошибка evidence, lease или commit не оставляет новый отчёт в каталоге.
5. Агент вызывает `actions.request` с `{kind:'lifecycle',changeSetId,version,validationId}`.
   Пользователь подтверждает конкретное pending action через защищённый HTTP API.
   Агент не может выдать себе разрешение. Обычные ACP permissions и autoApprove
   пользовательское подтверждение не заменяют.
6. `actions.status({id})` возвращает requesting live session состояние запроса
   и authorizationId после подтверждения. Другие сессии и валидатор его не получают.
7. `change_sets.commit({id,version,validationId,authorizationId,requestId})` применяет
   пакет атомарно. Replay того же requestId возвращает прежний результат; повторное
   потребление разрешения с другим requestId запрещено.

Manifest включает объединение текущего и предложенного графов, lineage,
контекст связанных задач и общих принятых документов и обязательные тексты.
Новые узлы учитываются через validationEpoch; metadataVersion внутри
области тоже обязана совпадать. Перед commit сервер проверяет физические файлы.
Manifest использует rulesVersion=2. Проверки старой версии требуют нового prepare;
их metadata, история и отчёты остаются доступны для чтения. Свежесть проверяется
до создания отдельного report-артефакта.

## Разрешения валидатора

Валидатор получает фиксированную серверную политику при запуске. Подтверждения
`validations.get`, `validations.manifest`, `validations.read`, `validations.submit`,
`validations.create_report` и `artifacts.get_content` выдаются автоматически только
для текущего назначения и содержимого его манифеста. Каждое разрешение относится
к одному вызову; общее `autoApprove` для валидатора включить нельзя.

Другие запросы разрешений, неверные аргументы и неизвестные форматы адаптера
автоматически отклоняются. Причина видна в ленте инструментов. Поддерживаются
структурированное имя инструмента Claude и коррелированные MCP approvals Codex;
название действия в заголовке не используется для выдачи разрешения.
Обычные чаты сохраняют ручные подтверждения и свой переключатель `autoApprove`.

Эта политика регулирует ACP permissions, а не заменяет ОС-песочницу:
действия, которые сам CLI выполняет без запроса разрешения, требуют его собственных
ограничений. Проверки доступа на HTTP/MCP bridge остаются обязательными.

## HTTP

| Метод и путь | Действие |
|---|---|
| POST `/api/artifact-change-sets` | Предложить пакет или новую immutable версию |
| GET `/api/artifact-change-sets/:id` | Текущая версия предложения |
| POST `/api/artifact-validations` | Prepare: `{changeSetId,version}` |
| POST `/api/artifact-validations/:id/start` | Start: `{presetId}` |
| GET `/api/artifact-validations/:id` | Статус и краткая сводка отчёта |
| GET `/api/artifact-validations/:id/manifest` | Страницы manifest, `limit/cursor` |
| GET `/api/artifact-validations/:id/report` | Полный структурированный отчёт блоками, `offset` |
| GET `/api/artifact-validations/:id/history` | Immutable история, `afterSeq/limit` |
| DELETE `/api/artifact-validations/:id` | Отменить проверку |
| GET `/api/artifact-actions` | Store ID и pending actions для подтверждения |
| GET `/api/artifact-actions/:id` | Точная область, readiness, текущая фаза и доступность исполнения |
| GET `/api/artifact-validations/:id/check` | Зафиксированная версия предложения, preview и readiness проверки |
| POST `/api/artifact-actions` | Предложить конкретное действие от пользователя |
| POST `/api/artifact-actions/:id/approve` | Подтвердить с `{sourceUserRequestId}` |
| DELETE `/api/artifact-actions/:id` | Отозвать pending action или grant |
| POST `/api/artifact-change-sets/:id/commit` | Атомарно применить подтверждённый пакет |

Agent bearer не действует на пользовательских HTTP API. Уведомление
`artifact-actions` идёт через существующий `/api/agent/events`; новый EventSource
не нужен. Grant привязан к сессии, точному digest и manifest, действует 15 минут,
используется один раз и не восстанавливается после restart.

Ревью артефактов удалено по ADR 0097. Запросы разрешений принимают только
`kind:'lifecycle'`. Исторические таблицы обсуждений сохраняются без активных API.

## Статусы и сбои

Команды пакета: `return_to_draft`, `reject`, `accept`, `archive`, `delete`,
`restore`, `update_relations`. Принятие возможно напрямую из draft через validation
и разрешение пользователя. Исторический in_review допускает принятие или возврат
в draft. Новые submit_review запрещены; старые предложения доступны только для
чтения и не могут исполняться.
`restore` возвращает archived/deleted в draft. История superseded навсегда
запрещает восстановление прежнего документа: нужен новый артефакт.

При замене accepted предшественник получает superseded. Для каждого активного
дополнения требуется incorporated → archived + includedIn audit, carry_forward →
accepted с новой базой, либо obsolete → archived/deleted. Исторические priority
связи сами по себе не активны; активен только accepted source.

Одновременно работает одна validation job на store, включая несколько serve.
Timeout — 10 минут. Отмена, завершение агента без отчёта и отзыв сессии не дают pass.
После restart история и prepared/report записи сохраняются. Проверка с умершим
owner или истёкшей lease становится incomplete; чужая активная lease сохраняется.

Изменившийся manifest, неверное разрешение или сбой записи
отклоняют весь commit. SSE отправляется после успешной транзакции. Отчёт является
свидетельством процедуры; сервер не доказывает смысловую правильность анализа.

## Интерфейс очереди запросов (исторический, не подключён)

**Состояние на 2026-11-01:** стор и composable очереди (`artifact-actions-store`,
`use-artifact-actions`) и серверные маршруты существуют, но ни одна страница не
монтирует этот экран. Пользовательский путь смены статуса — кнопка в шапке
документа (раздел ниже). Описание ниже сохранено как контракт экрана, который
может быть подключён позже; не считать его текущей возможностью интерфейса.

Кнопка действий на `/artifacts` открывает очередь запросов и вкладку ChangeSet.
Предложение открывается по ID; `changeSetId`, `validationId` и `actionId` в query
позволяют восстановить экран после перезагрузки. UI показывает команду, автора,
версию, digest, subject IDs, ожидаемые metadata versions, явные целевые статусы,
полные заменяемые списки связей и решения для активных дополнений. Изменения
содержимого документа здесь не поддерживаются.

Для предложения можно подготовить новую проверку, выбрать доступный серверный
preset, запустить отдельного валидатора и отменить prepared/running job.
Полный структурированный отчёт читается по запросу после завершения проверки.
Клиент проверяет непрерывность UTF-8 блоков и идентичность отчёта; при размере
более 16 MiB показывает ошибку, не скрывает часть findings.

Свежий совпадающий pass позволяет запросить разрешение от текущего пользователя.
Каждое подтверждение требует отдельного checkbox для показанной области.
Изменение данных, потеря свежести и восстановление соединения сбрасывают checkbox.
Подтверждение выдаёт grant; отдельная кнопка «Применить» выполняет user-bound action.
Для agent-bound action UI только подтверждает запрос: grant получает и использует
исходная сессия через `actions.status`. Отзыв работает и по исходному pending ID
после выдачи grant. Повтор подтверждения с тем же sourceUserRequestId возвращает
тот же непросроченный grant при неизменной области.

Изменения поступают через общие `/api/events` и `/api/agent/events`; дополнительных
EventSource нет. Grants не записываются в browser storage. Сервер повторно
проверяет область перед выдачей разрешения и применением пакета.

## Недоступное содержимое (ADR 0109)

Если тело документа не читается, метаданные, история, связи и выгрузка
metadata-history остаются доступны: сервер читает их без тела. Тело заменяется
ошибкой с «Retry». Фоновые обновления не повторяют чтение после ошибки; снимает её
только «Retry» или «Refresh» шапки (оба принудительно читают и проверяют все
чанки заново) либо выбор другого документа. Ошибка классифицируется по коду
`GHT_ARTIFACT_INTEGRITY` и локальным нарушениям цепочки чанков, не по тексту;
любой другой сбой — транспортный. При известной порче выгрузка оригинала и «Add to
agent» отключены, новый запуск смены статуса разрешён только при проверенном
содержимом; прогресс и отмена запущенной операции доступны всегда.

## Смена статуса кнопкой (ADR 0107)

В шапке открытого документа статус — кнопка. Меню содержит только допустимые
целевые статусы: `in_review` и `superseded` пользователь не назначает, документ с
историей `superseded` в `draft` не возвращается. Допустимость берёт общая матрица
`src/shared/artifact-transitions/transitions.ts`, её же использует серверная проверка.

Выбор статуса открывает диалог: что будет изменено, включая замену предшественника,
выбор валидатора и «Да» / «Нет». Валидатор не запускается до «Да». Последний
успешно отправленный пресет подставляется; недоступный не заменяется. Единственное
«Да» создаёт **предварительное согласие** и **операцию перехода**: подготовка,
проверка, применение при свежем pass. Повторного подтверждения при неизменной области
нет. Диалог закрывается, стадия и отмена видны у кнопки; закрытие вкладки операцию
не прерывает.

Ошибка агента, `conflict`, `incomplete`, таймаут, истёкшее согласие, изменение
области или отзыв доступа устройства не меняют статусы. «Повторить» открывает новый
диалог с новым preview и новым «Да». Отмена возможна до применения; запрос отмены
пишется в хранилище, процесс-владелец останавливает агента (в пределах интервала
сверки около 1 с). Остановка сервера помечает операцию `interrupted`. После жёсткого
сбоя другой процесс признаёт владельца мёртвым при отсутствии его процесса или при
устаревшем признаке жизни (30 с, ADR 0108): операция становится `interrupted` не
позднее порога плюс интервал сверки, аренда валидатора освобождается; после pass
она не применяется. Строки признака нет — владелец считается живым.

Ошибка занятости БД при commit не завершает операцию: она остаётся `applying`, и
следующая сверка повторяет commit с тем же `requestId`, пока действует согласие
(сама ошибка приходит после ожидания до 5 с). Если аренду валидатора заняли между
проверкой и стартом, «Да» получает `409` (`GHT_ARTIFACT_CONFLICT`), а запись
операции сохраняется как `failed`; подготовленные proposal и validation остаются.
Завершённая операция показывается в панели 10 минут, полный результат — в окне
«Результат проверки» (findings и resolutions отчёта валидатора). Отменить операцию
может любой пользовательский доступ; ключ агента на этих маршрутах не действует.

Известное ограничение: если у базового документа есть активные дополнения,
`archive`/`delete` блокируются с объяснением; выбрать их решения в этом экране нельзя.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/artifacts/:id/transitions` | доступные статусы и активная операция |
| POST | `/api/artifacts/:id/transition-previews` | точные последствия, живут 10 минут в памяти |
| POST | `/api/artifact-transition-operations` | «Да»: `previewId`, `presetId`, `requestId` |
| GET | `/api/artifact-transition-operations/:id` | чтение операции |
| GET | `/api/artifacts/:id/transition-operations` | последние операции документа |
| POST | `/api/artifact-transition-operations/:id/cancel` | запрос отмены до применения |

Маршруты принимают только пользовательский доступ; ключ агента не действует. Старые
MCP `actions.request` и HTTP approve работают как раньше и общего разрешения до pass
не получают.
