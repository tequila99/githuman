# Контекст запроса к агенту: URI и блоки

Как элементы контекста чата (`diff`, `file`, `directory`, `review`, `note`, `artifact`, `attachment`) превращаются в блоки запроса ACP.
Код — `src/server/services/agent/context-builder.ts`, схема элементов — `src/shared/agents/schemas.ts`
(`ContextItem`). Термины — в [глоссарии](GLOSSARY.md).

## Что такое `githuman://`

`githuman://…` — идентификатор встроенного ресурса (`resource.uri`) в запросе ACP. Это **не адрес**: по
нему нельзя ничего открыть или скачать, и сам githuman его нигде не разбирает. Идентификатор нужен агенту,
чтобы назвать источник текста («diff из индекса», «ревью»), и ACP требует поле `uri` у ресурса.

| Вид | URI | Источник | Кодирование |
|---|---|---|---|
| `diff` | `githuman://diff/<source>/<path>` | `source` — `staged` или `unstaged`; `path` — путь файла в diff, может отсутствовать | `path` не кодируется. Без пути URI заканчивается на `/` |
| `note` | `githuman://note/<storageId>/<noteId>` | текущий Markdown заметки по UUID и хранилищу | `encodeURIComponent` для обоих идентификаторов |
| `artifact` | `githuman://artifact/<storeId>/<artifactId>` | immutable document и актуальные metadata/links, прочитанные сервером перед prompt | `encodeURIComponent` для обоих идентификаторов |
| `review` | `githuman://review/<id>` | `id` ревью | не кодируется |
| `attachment` | `githuman://attachment/<имя>` | имя файла, которое прислал клиент (только текстовые вложения) | `encodeURIComponent` |

## Как элемент контекста попадает в запрос

Запрос — это текст пользователя, затем по одному блоку на каждый элемент контекста (`buildPromptBlocks`).

| Элемент | Блок ACP | Условия |
|---|---|---|
| `diff` (текст изменений) | `resource` с `githuman://diff/…`, тип `text/x-diff` | агент объявил `embeddedContext`; иначе — обычный текстовый блок с кодовой оградой, URI **отбрасывается** |
| `note` (заметка с YAML-свойствами, название и путь) | `resource` с `githuman://note/…`, тип `text/markdown` | `embeddedContext`; иначе — текст с кодовой оградой. Сервер читает актуальную сохранённую версию по UUID; связанные заметки и изображения не включаются |
| `artifact` (документ, актуальные metadata, входящие и исходящие links) | `resource` с `githuman://artifact/…`, тип `text/markdown` | `embeddedContext`; иначе fenced text. Клиент передаёт только store/artifact ID и display name, сервер проверяет физический файл |
| `review` (ревью с комментариями, markdown) | `resource` с `githuman://review/…`, тип `text/markdown` | то же |
| `attachment`, текст в UTF-8 | `resource` с `githuman://attachment/…` | то же |
| `file` (файл репозитория) | `resource_link` с `file://` | агент читает файл сам, в том же `cwd` |
| `directory` (директория репозитория) | `resource_link` с `file://…/`, имя `путь/` | агент читает директорию сам. У ACP нет типа для директории, поэтому признак — завершающий `/` в URI и имени. Корень репозитория не принимается: это и так `cwd` агента |
| `attachment`, изображение | `image` | агент объявил `image`, иначе ошибка «This agent does not accept images» |
| `attachment`, остальное (PDF, архив, не UTF-8) | `resource_link` с `file://` на копию в каталоге вложений | копия лежит вне репозитория |

Текст длиннее `MAX_EMBEDDED_CHARS` (200 000 символов) обрезается маркером
`… [truncated by githuman: N more characters]`: агент видит, что его обрезали и кто это сделал.
Вложение больше `MAX_ATTACHMENT_BYTES` (10 МБ) отклоняется.

Упоминание `@путь` остаётся в тексте запроса как метка, а редактор отдельно добавляет элемент контекста
с тем же путём (повторы убираются): `file` для файла и `directory` для директории. Путь директории в
поиске, чипе и тексте заканчивается на `/` (`@src/web/`), а в элементе `directory` хранится без него.
Директории поиск выводит из списка файлов (`git ls-files`). Подмодуль git и символическая ссылка на
директорию выглядят в этом списке как файл: их упоминание как файла даёт ошибку «is not a file» —
известное ограничение. Файл или директория, чей реальный путь (`realpath`) лежит вне репозитория,
отклоняется. Сам файл или директория уходят один раз, как
`resource_link`, а метка в тексте показывает агенту, о чём речь.

## Как добавить новый вид элемента

1. Добавить вариант в `ContextItem` (`src/shared/agents/schemas.ts`).
2. Написать `build<Вид>Item` в `context-builder.ts` и добавить ветку в `buildItem`.
3. Для встроенного текста взять `embed(...)` и новый URI вида `githuman://<вид>/…`; записать его в таблицу выше.
4. Показать элемент в интерфейсе: `src/web/components/agent/` и `src/web/utils/agent-context-label.ts`.
5. Добавить тест в `tests/server/routes/agent.test.ts`.

## Артефакты и связанные документы

Кнопка Add document to agent chat в просмотре артефакта добавляет его в активный
чат или открывает создание чата с этим контекстом. Повтор одного storeId/artifactId
не добавляет второй элемент при изменении display name. Перед отправкой сервер
проверяет хранилище и SHA-256 файла, читает актуальные metadata и обе страницы
связей в одном SQLite snapshot. Заголовок чипа — подпись на момент добавления;
он не подменяет серверные данные.

JSON metadata snapshot идёт перед body и содержит storeEpoch, текущий artifact,
входящие/исходящие edges с nextCursor. Body извлекается без исторического
frontmatter. Лимит MAX_EMBEDDED_CHARS применяется к body, а metadata и инструкции
продолжения сохраняются целиком. При усечении агент читает исходный файл через
`artifacts.get_content({id,offset:0})`, следуя byte-based nextOffset; bodyStartLine
показывает начало body. Полные списки связей читает через `artifacts.relations`
с direction и cursor. Смена epoch требует начать pagination заново.

Тексты связанных документов автоматически не включаются. Агент самостоятельно
получает их через `artifacts.get` и `artifacts.get_content`, проверяет статус и
отличает исторические документы от действующего accepted-контекста. Для ссылки
в ответе использует `/#/artifacts?storeId=<storeId>&selectedId=<artifactId>`.
URI `githuman://artifact/…` остаётся идентификатором ACP ресурса.


### Граница префикса артефакта

Консервативная граница проверяется в `artifact-context.test.ts`: **85 680 байт**
UTF-8 до `Document body`. Расчёт: 65 536 байт JSON входных metadata (серверный
лимит, включая escaping), две страницы по 50 edges × 140 байт плюс по 1 024
байта на обрамление и cursor, ещё 4 096 байт на identity, revisionOf (максимум
один UUID), числовые поля и инструкции. Edge содержит два UUID и kind;
140 байт покрывают наиболее длинный допустимый kind. Обычный размер страницы
задаёт `DEFAULT_ARTIFACT_PAGE_SIZE`; тест намеренно фиксирует 50 и полные
страницы в обоих направлениях, чтобы изменение лимита требовало пересмотра
расчёта. Максимумы полей: title 1 000 символов, 100 tags по 128, 100 taskIds,
200 relations, typeId 100. Общий byte limit не позволяет одновременно заполнить
все текстовые поля символами с шестибайтным JSON escaping; тест сочетает
максимумы количества/длины с control characters в части полей.

Это отдельный ограниченный бюджет metadata, а не часть `MAX_EMBEDDED_CHARS`
(200 000 символов body). Тексты связанных документов в него не входят.
Текущая граница принята без дополнительного усечения; nextCursor и инструкции
получения полного содержимого сохраняются.

## Задача текущего ответа и создание артефактов

Для GitHuman-hosted сессии сервер отдельно фиксирует задачу на начало ответа:
серверный ID turn, ID сессии, версию назначения и копию назначенных task IDs.
Это не извлечение задачи из URI, названия чата или содержимого документа.
`artifacts.create` без `metadata.taskIds` наследует задачу только при одном
назначенном ID. Явный `[]` означает создание общего документа. При отсутствии
единственного выбора сохраняется прежний результат `[]`.

Контекст снимается при фактическом принятии prompt, после подготовки вложений,
и сохраняется до завершения/отмены ответа. Ручная смена выбора в интерфейсе
действует со следующего сообщения. Явная MCP-активация через `tasks.activate`
или `tasks.create_and_activate` заменяет снимок текущего ответа после commit:
последующие артефакты наследуют выбранную задачу, прежние остаются на месте.
Ранее выданные объекты снимка не меняются. Разные сессии имеют разные снимки.

Перед каждой активацией агент читает `tasks.get_context` и передаёт полученные
`turnId` и `assignment.version` без изменений. При конфликте он перечитывает
контекст и уточняет выбор у пользователя. `tasks.create` только создаёт задачу.
Если пользователь просит активировать несколько задач без выбора одной, агент
создаёт их без активации и спрашивает, какую выбрать. Активация закрытой задачи
не открывает её. После отмены `turnId` равен `null`, активация недоступна.
Снимок не является новой частью публичного ArtifactSchema и не предоставляет
внешним native CLI/IDE доступ к истории или автоматическое определение задачи.
