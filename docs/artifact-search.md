# Поиск артефактов

Поиск работает локально по текущему title и неизменяемому body. По умолчанию
возвращает accepted; draft, rejected, superseded, archived и deleted выбираются
явным фильтром. Пустой запрос возвращает каталог с теми же фильтрами.

## API и MCP

- `GET /api/artifacts/search?query=текст&mode=auto&status=accepted&limit=20`.
  Дополнительные одиночные фильтры: `typeId`, `taskId`, `tag`.
- `POST /api/artifacts/search` и MCP `artifacts.search` принимают общий объект:

```json
{
  "query": "проектирвоание",
  "mode": "auto",
  "filters": {
    "statuses": ["accepted"],
    "typeIds": ["generic"],
    "tags": ["architecture"]
  },
  "sort": "relevance",
  "limit": 20
}
```

`filters.taskIds` выбирает любой из указанных UUID задач; tags требуют все
перечисленные теги. Фильтры выполняются до LIMIT. Сортировки `createdAt` и
`metadataUpdatedAt` идут от новых документов к старым. При непустом запросе
по умолчанию используется relevance; при пустом — createdAt.

Ответ содержит `items`, `storeEpoch`, `indexEpoch`, `nextCursor`, `partial` и
`reason`. Следующая страница получает исходные параметры и `cursor=nextCursor`;
limit можно изменить. Курсор связан с запросом, фильтрами, сортировкой, store
и поколением индекса; изменение данных требует начать чтение заново. Варианты
исправлений зафиксированы в курсоре, а не пересчитываются на каждой странице.
Если при чтении страницы по курсору обнаружен corrupt/missing файл, его
suppression сохраняется, а запрос получает 409: пагинацию нужно начать заново.
Первая страница в такой ситуации пересобирается автоматически. Если повреждён
только дополнительный результат `limit + 1`, он будет проверен на следующей
странице; там также возможен 409.

Пока FTS-таблицы и статистика BM25 общие для всех store этой БД, `indexEpoch`
тоже общий. Запись в чужой store может изменить порядок результатов и требует
перезапуска курсора. Независимую epoch нельзя включать без изоляции статистики
ранжирования; это открытый пункт C1 плана исправлений.

Для обычного HTTP действуют локальный доступ или сопряжённое устройство.
MCP использует ключ сессии и существующий bridge. Служебный validation agent
не получает поиском доступ за пределы своего manifest.

## Совпадения и цитаты

`mode=exact` ищет буквальную нормализованную подстроку и все точные токены.
`mode=auto` и `mode=fuzzy` дополнительно рассматривают исправления опечаток.
Кавычки, AND/OR/NOT и SQL-фрагменты являются текстом, а не языком запросов.

Нормализация: NFC, lowercase и ё→е. Для терминов до трёх Unicode codepoints
опечатки не исправляются; длина 4–7 допускает одну правку, от восьми — две.
NUL в query отвергается с HTTP 400 (в GET, POST и MCP), без молчаливого удаления.
Учитываются вставка, удаление, замена и перестановка. На термин используется
до восьми вариантов. Запрос ограничен 256 codepoints и восемью токенами.
Морфология, embeddings и смысловая близость не входят в этот этап.

При relevance точные подстроки стоят выше точных токенов, затем идут исправленные
совпадения; далее BM25 и ID. `matchKind` различает `exact`, `exact_normalized`,
`token`, `fuzzy` и `catalog`. Нечёткий результат не выдаётся за точную цитату запроса.

Snippet — plain text из оригинала, до 640 UTF-16 code units без разрыва surrogate pair. Highlights содержат
UTF-16 диапазоны внутри этой строки. Сопоставление NFC и изменения длины lowercase
переводятся обратно в исходные диапазоны через сохранённый offset mapping.
HTML-маркеры не вставляются. Body anchor содержит неизменяемые hash/line numbers
и полную исходную цитату строк до 8 KiB; для title и слишком длинных строк
anchor=null. Это предотвращает выдачу частичной строки за точную привязку к исходнику.

## Индекс и ограничения

FTS5 unicode61 обслуживает токены, trigram — подстроки от трёх codepoints.
Более короткие запросы используют параметризованный LIKE с escaping `%`, `_`
и обратной косой черты. Словарь с length/ngram postings ограничивает кандидатов,
затем bounded Damerau–Levenshtein проверяет расстояние.

На термин обрабатывается до 2048 кандидатов; временной бюджет fuzzy — 150 мс
без учёта уже выполняющегося SQL. При ограничении ответ возвращает
`partial=true` и reason. Точные результаты сохраняются. Нельзя трактовать такой
ответ как доказательство отсутствия других нечётких совпадений.

GET и POST поиска могут достраивать индекс после миграции и подавлять
повреждённые документы, поэтому эти чтения могут менять `indexEpoch`.
Авторитетные файлы, snapshots и история при этом не меняются.

Проекции обновляются синхронно с metadata commit; нормализованная копия body строится
при первом появлении, title — при изменении нормализованной копии.
После миграции старые записи достраиваются при первом поиске. Rebuild доступен
внутреннему сервису `storage.search.rebuild()`, выполняется синхронно и не меняет
файлы, snapshots, metadataUpdatedAt или историю. Это операция обслуживания,
а не действие агента. Полный rebuild инвалидирует старые курсоры.

`GET /api/artifacts/search/diagnostics` сообщает доступность, число документов
и IDs подавленных записей. Файл проверяется при выдаче результата. После обнаружения
missing/corrupt документ исключается из индекса; изменённые внешним процессом байты
автоматически не принимаются. Rebuild повторно проверяет исходный hash.

Отсутствие unicode61/trigram даёт `503 GHT_ARTIFACT_SEARCH_UNAVAILABLE`, обычное
чтение документов остаётся доступным. Индекс не является источником содержимого.

## Измерения

Linux, Node 24.2.0 / SQLite 3.50.0, Xeon E5-2678 v3, 10 000 документов,
ровно 100 MiB body и 100 000 событий истории: максимальный warm p95 exact
237 мс, auto/fuzzy 490 мс, по 25 измерений каждого запроса. Индекс — около
501 MiB, БД — около 720 MiB. Один плотный auto-запрос достиг fuzzy budget и
возвращал partial; точный результат сохранился. Это измерения синтетического
корпуса, не обещание для любого компьютера и словаря.

Повтор: `node tests/server/benchmarks/artifact-search.ts`. Скрипт создаёт временную
БД и файлы, печатает среду, объём, индекс и latency в JSON, затем удаляет корпус.
Основа алгоритма FTS описана в [SQLite FTS5](https://sqlite.org/fts5.html).
UI поиска и запуск исследования из интерфейса относятся к этапу 0094.


После ревью дополнительно измерен `create` на разнообразном словаре.
Три запуска в свежем in-memory SQLite с реальным временным файлом артефакта,
Node 24.2.0 / Xeon E5-2678 v3; ниже медианы до/после кэширования statements
и UPSERT RETURNING:

| Уникальных слов | До | После |
|---|---:|---:|
| 1 000 | 246 мс | 94 мс |
| 20 000 | 5 623 мс | 1 661 мс |

Запись большого словаря по-прежнему синхронная и занимает секунды.
Основной корпус 10k/100 MiB в основном повторяет небольшой набор слов; его
fuzzy-latency не характеризует большой разнообразный словарь. Старые p95 выше
измерены до исправлений ревью и не выдаются за новый замер изменённого ranking SQL.
Отдельный быстрый замер: `node tests/server/benchmarks/artifact-search-vocabulary.ts`.
Полный benchmark теперь тоже добавляет отдельное поле `vocabularyCreate`;
это отдельная временная БД, не меняющая заявленные 10k документов/100k событий.
