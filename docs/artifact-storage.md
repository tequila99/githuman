# Хранилище артефактов: эксплуатация основания 0088

Артефакты принадлежат репозиторию. Неизменяемые Markdown-файлы находятся в
`.githuman/artifacts/<prefix><UUID>.md`, каталог и история — в существующей
`.githuman/<prefix>reviews.db`. По умолчанию prefix — `ght-`; используется
тот же `--db-prefix` / `GITHUMAN_DB_PREFIX`, что для reviews и notes.

На этапе 0088 доступны только HTTP-чтение и внутренний серверный сервис.
Добавление агентом через MCP, связи, принятие, комментарии и UI реализуются
следующими этапами. Внутренний документ имеет тип `generic` и статус `draft`.

## Источники данных

Файл содержит YAML frontmatter начального состояния и исходный текст.
Frontmatter после создания не меняется. Актуальные title/tags и версия берутся
из БД; дата изменения относится к метаданным. SHA-256 охватывает весь файл,
включая frontmatter. Максимум файла — 2 MiB; текст ограничен 1.9 MiB,
JSON метаданных — 64 KiB. Контент возвращается UTF-8 блоками до 64 KiB.

Авторитетны `artifacts`, `artifact_stores`, `artifact_metadata_versions`,
`artifact_events`, `artifact_operations`, `artifact_operation_events`.
UPDATE/DELETE и замена существующей записи через REPLACE запрещены триггерами.
`artifact_current`, `artifact_store_epochs` — перестраиваемые проекции;
`artifact_operation_leases` — временное владение незавершённой операцией.

## Резервная копия и восстановление

1. Остановить **все** процессы GitHuman, использующие этот репозиторий,
   включая другие экземпляры serve и команды записи. Не копировать работающую БД.
2. Скопировать целиком `.githuman/` вместе с БД, `-wal` / `-shm`, если они
   остались после остановки, и `artifacts/`. Сохранить режимы доступа.
   Копия только `.db` или только Markdown не является полной копией.
3. Для восстановления использовать пустой целевой каталог репозитория
   или предварительно сохранить текущую `.githuman/` отдельно. Не смешивать
   файлы и БД разных резервных копий.
4. Восстановить `.githuman/` целиком; запускать с прежним префиксом.
   БД должна находиться по штатному пути `.githuman/<prefix>reviews.db`.
   Перенос в другой корень сохраняет `storeId`; копия считается тем же store.
   Разветвление идентичности копии в новый независимый store пока не поддержано.
5. Запустить сервер. Recovery выполняется при старте и каждые две секунды.
   После аварийного завершения чужой lease может действовать до 30 секунд.
6. Проверить каталог, историю и прочитать содержимое каждого документа до
   `nextOffset: null`: чтение проверяет размер и SHA-256 всего файла.
   Сверить число документов, ID и версии с контрольным списком копии.

Никакие неизвестные Markdown-файлы автоматически не импортируются. Не удалять
orphan/temp-файлы вручную до диагностики: temp может быть единственной
сохранённой копией текста pending-операции.

## Recovery и повтор запросов

- До сохранения полного текста операция остаётся `awaiting_retry` и не видна
  в каталоге. Повторить исходные requestId, body, metadata и actor через
  внутренний сервис (позднее — MCP). ID и время создания сохраняются.
- После сохранения temp или публикации final recovery проверяет hash,
  синхронизирует файл, завершает commit и записывает ровно одно событие создания.
- Публикация использует эксклюзивный hard link; существующий final никогда
  не перезаписывается. Необходима локальная файловая система с hard links.
- При несовпадении final/hash операция получает `failed`. Сначала восстановить
  согласованную резервную копию либо исследовать причину повреждения.
  Изменять hash в истории, перезаписывать final или удалять события нельзя.
- SQLite ждёт освобождения блокировки до пяти секунд. Истёкшее ожидание
  серверного artifact-сервиса даёт конфликт, после которого допустим повтор
  с прежним requestId. Иной payload с тем же requestId запрещён.

Внутренние `ArtifactStorageService.diagnostics()` и `recover()` позволяют
исследовать orphanFiles и состояния операций. `service.catalog.rebuild()`
транзакционно восстанавливает current и epoch из авторитетных записей;
это средство обслуживания, HTTP-команды для него нет. Выполнять обслуживание
на остановленном экземпляре, после резервной копии, с проверкой контента.
Rebuild не восстанавливает потерянные Markdown-файлы.

## API чтения

- `GET /api/artifacts?limit=50&cursor=...`: каталог, storeId, storeEpoch,
  items и nextCursor. После изменения epoch старый cursor даёт 409;
  загрузку списка нужно начать сначала. Максимум страницы — 100.
- `GET /api/artifacts/:id`: актуальные метаданные.
- `GET /api/artifacts/:id/content?offset=0&limit=65536`: текст, hash,
  bodyStartLine, totalBytes и nextOffset. Offset измеряется в байтах и должен
  совпадать с границей UTF-8 символа.
- `GET /api/artifacts/:id/history?afterSeq=0&limit=50`: неизменяемая история.

Отсутствующий ID — 404; отсутствующий или повреждённый файл известного ID —
422 `GHT_ARTIFACT_INTEGRITY`. Контент не подменяется пустой строкой. Маршруты
используют общую проверку доступа устройств. SSE `artifacts:changed` содержит
storeId/storeEpoch и означает необходимость перечитать состояние после commit.
После переподключения клиент должен перечитать каталог независимо от SSE.

## Проверенные гарантии и ограничения

Автоматические проверки Linux покрывают сбои на границах протокола,
частичный temp, конфликтующий final, symlink, повреждение файла, конкурентные
процессы, откат транзакции, восстановление копии и повтор requestId.
Они моделируют прерывание процесса, но не физическое отключение питания.

Windows/NTFS в текущем окружении не проверены. File fsync использует writable
handle; directory fsync пропускается на Windows, поскольку Node не открывает
каталоги для этой операции. До выпуска записи на Windows обязательны отдельные
испытания publish/recovery и проверка гарантий сохранности. Сетевые файловые
системы и одновременная враждебная подмена каталогов на диске не входят в
проверенную модель; защитные проверки не заменяют права доступа ОС.

## Фоновое обслуживание

`ArtifactMaintenanceService` запускается в `onReady` приложения и останавливается
в `onClose`. Конструктор не запускает фоновые задачи. `start()` сначала выполняет
полное recovery и проверку epoch; их ошибки передаются обработчику и **не**
блокируют запуск сервера: чтение проверяет SHA-256 каждого файла, а повтор идёт
каждые две секунды. Таймер создаётся всегда. Повторные `start()`/`stop()`
безопасны; после остановки сервис можно запустить снова.

Каждые две секунды сервис восстанавливает незавершённые операции и отдельно
проверяет epoch. Ошибка восстановления не блокирует проверку изменений другого
процесса. Фоновые ошибки передаются внедрённому обработчику с фазой `recovery`
или `poll`; повторяющаяся ошибка с тем же текстом сообщается один раз, пока
очередной проход не завершится успешно. Следующий проход остаётся запланирован.
Операции синхронные. `ArtifactStorageService.recover()` обрабатывает все
операции за один проход: непредвиденная ошибка одной операции не останавливает
остальные, а после прохода пробрасывается (несколько ошибок — `AggregateError`
с `requestId` каждой операции). `recover()` самостоятельно расписанием не
управляет; уведомления о собственных commit сохраняются, проверкой сторонних
изменений управляет сервис обслуживания через `pollChanges()`.

## Известные ограничения эксплуатации

- **Задержка из-за блокировки БД.** `node:sqlite` синхронный, а `busy_timeout`
  равен пяти секундам. Пока другой процесс держит блокировку записи, запись
  артефакта или recovery может остановить обработку всех запросов `serve` до
  пяти секунд.
- **Симлинк `.githuman`.** Каталог `.githuman` и `.githuman/artifacts` должны
  быть обычными каталогами. Симлинк на другой диск не поддерживается: чтение и
  recovery вернут `GHT_ARTIFACT_INTEGRITY`.
- **Стоимость чтения.** Каждый запрос чанка читает и проверяет SHA-256 всего
  файла (до 2 MiB), поэтому полное чтение документа повторяет эту работу для
  каждого блока.
- **Префикс.** `serve` отвергает `--db-prefix` / `GITHUMAN_DB_PREFIX` с символами
  `< > : " / \ | ? *`, управляющими символами или длиннее 100 символов. `list` и
  `export` префикс не проверяют. Пустой префикс допустим.
