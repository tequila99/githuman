# Идентичность и навигация заметок

Заметка имеет стабильный UUID в SQLite-каталоге. Текст остаётся UTF-8 Markdown на диске. Полное имя файла — изменяемое свойство, не идентификатор. Область идентичности — пара `storageId` и `noteId`.

## Файлы и переносимость

Новые заметки приложения получают `githuman_id` в YAML. Внешние файлы при регистрации не переписываются. Отсутствие или удаление этого поля не мешает чтению и сохранению; существующий файл по прежнему пути сохраняет идентичность каталога. Конфликтующее/повторяющееся поле даёт диагностику, а не объединение файлов.

Ссылки в Markdown остаются обычными относительными путями с кодированием специальных символов и необязательным якорем. При копировании дерева заметок без БД они работают в другом редакторе. ID внутри YAML помогает восстановить идентичность после переноса, но история путей и удалений остаётся в БД; старые адреса приложения содержат прежний storageId и не разрешаются молча в другую копию.

БД содержит каталог, историю путей, связи, диагностические решения и журнал незавершённых операций. Она использует существующий SQLite-файл приложения. Для переноса вместе с БД требуется осознанная перепривязка корня хранилища; автоматического угадывания по похожим файлам нет.

## Навигация

Канонический адрес — `#/notes/<storageId>/document/<noteId>`. Вход `#/notes?file=<relative-path>` разрешается в UUID и заменяется каноническим адресом. Повторно использованный исторический путь может быть неоднозначным; тогда нужен UUID. Каталоги открываются через `#/notes?folder=<relative-path>`.

В панели доступны Back/Forward; работает и история браузера. Переход сначала сохраняет черновик. Невалидный YAML, ошибка записи и конфликт останавливают уход, сохраняя текст. Возврат восстанавливает режим редактора и прокрутку отдельно для каждого посещения, включая переходы по якорям. После перезагрузки открывается заметка из URL, но история режимов/прокрутки текущей сессии не сохраняется на диск.

Кнопки вызывают стандартные `router.back()` / `router.forward()` без собственного списка доступных переходов. Они остаются активными; при отсутствии записи в нужном направлении переход не происходит. Возврат может вывести за пределы приложения. `useNotesHistoryState` хранит только состояние просмотра, привязанное к записям истории роутера.

## Переименование и перемещение

Контекстное меню дерева и каталога открывает Rename. Дополнительное поле Destination folder позволяет переместить элемент. UUID и адрес заметки сохраняются.

Обновляются входящие ссылки на перемещённые заметки и исходящие относительные ссылки перемещённых источников. Локальные изображения и вложения участвуют в пересчёте адресов, но не становятся узлами графа заметок. Внешние URL и `/api/notes/assets/...` не изменяются. Сохраняются подписи, якоря, код, остальное форматирование и YAML-комментарии. Поддерживаются inline-ссылки и reference definitions, а также уже поддерживаемые wiki-значения свойств YAML. Wiki-ссылки в теле и ссылки внутри raw HTML автоматически не переписываются.

Перед операцией проверяются ревизия каталога и версии файлов. SQLite и файловая система не являются общей транзакцией: intent и шаги сохраняются в журнале, который проверяется после перезапуска. Чужие изменения не откатываются. Незавершённые правки показываются в Notes; Retry link repairs исправляет узнаваемые ссылки в свежем тексте, сохраняя остальные правки. Неоднозначные вхождения требуют ручного исправления адреса. Резервные тексты завершённой операции удаляются из журнала; `.history` продолжает хранить одну предыдущую версию каждого записанного файла.

Одно хранилище имеет один пишущий процесс приложения, независимо от пути БД. Владение фиксируется скрытым `.githuman-writer.lock` в корне заметок. Другой процесс не получает права записи. Блокировка не истекает по таймауту; после аварии автоматически снимается только блокировка заведомо отсутствующего процесса на том же компьютере. Не удаляйте её, пока владелец работает. Внешние редакторы не участвуют в блокировке: проверки версий обнаруживают изменения, но не дают строгий filesystem compare-and-swap.

## Внешние изменения и отсутствие файла

Полная сверка выполняется при запуске и периодически. Уникальный сохранённый YAML-ID позволяет сопоставить внешний перенос с прежней заметкой и исправить ссылки. Короткое исчезновение при атомарном сохранении не считается новым документом.

Без ID однозначное распознавание произвольного внешнего переноса невозможно. Для файлов с подходящими признаками показываются действия This is the previous note / This is a new note / Later. Совпадение хеша — кандидат, не доказательство. Если заметка одновременно переименована и изменена без ID, автоматический кандидат может не найтись: поле Moved file позволяет выбрать файл явно. Confirm deletion сохраняет запись как удалённую; входящие связи остаются.

Отсутствующий файл сохраняет запись и входящие связи; переход по UUID показывает заглушку с последним путём и backlinks. Приложение честно сообщает, что файл может быть удалён или перемещён. Ошибка доступа или недоступность всего корня не объявляет все заметки удалёнными.

Возвращённый после устойчивого отсутствия файл без ID получает отдельную доступную запись до решения о восстановлении. Новый файл по старому имени не перехватывает прежние связи. Неоднозначное соответствие старой ссылки изменённому черновику блокирует переход вместо открытия предполагаемой цели.

## API и будущие функции

- `GET /api/notes` — дерево, storageId, revision и diagnostics.
- `GET /api/notes/by-id?id=...&storageId=...` — текст по идентичности.
- `GET /api/notes/identity?id=...&storageId=...` — присутствие и backlinks.
- `GET /api/notes/path?path=...` — разрешение текущего/исторического пути.
- `GET /api/notes/graph` — notes/edges по UUID; отсутствующие цели сохраняются.
- `POST /api/notes/resolve` — разрешение ссылки из актуального исходника/черновика.
- `POST /api/notes/rename` — переименование или перемещение с результатом complete/partial.
- `POST /api/notes/identity/resolve` — решение о восстановлении идентичности.
- `POST /api/notes/repair` — повтор незавершённых исправлений.

Будущий элемент контекста агента: `{ type: 'note', storageId, noteId }`. Имя берётся из каталога при отображении, текст — по ID при отправке. Отправленное сообщение должно фиксировать использованную версию/снимок; существующий `githuman://` пока не является разрешаемым агентом адресом заметки. UI чипа и диаграмма графа оформляются отдельными этапами.

### Markdown AST для будущей интеграции с LLM

Пакет `mdast-util-from-markdown` сейчас используется в `src/shared/notes/references.ts` для разбора ссылок с точными диапазонами в исходном Markdown. При интеграции заметок с LLM эту основу стоит переиспользовать. Текущий модуль извлекает ссылки; общего API для работы агента со структурой документа пока нет.

Возможные применения:

- Подготовка контекста по разделам и заголовкам, с сохранением границ списков и блоков кода. Ограничение размера контекста потребует отдельного подсчёта токенов.
- Извлечение ссылок для добавления связанных заметок в контекст через существующий каталог UUID, с явным ограничением глубины и объёма обхода.
- Адресные правки выбранного раздела или ссылки по диапазонам исходника, без пересериализации всего документа и потери постороннего форматирования.
- Проверка предложенных моделью правок: какие разделы и ссылки изменились, какие цели отсутствуют или неоднозначны.

Перед реализацией нужно согласовать поддерживаемый синтаксис с редактором: базовый Markdown AST не покрывает автоматически все расширения, wiki-ссылки и YAML. Frontmatter уже разбирается отдельно через `yaml`; существующие парсеры и resolver следует переиспользовать. Диапазоны относятся к конкретной версии текста: перед применением правки обязательны проверка версии и повторный разбор при её изменении. AST сам по себе не гарантирует корректность ответа LLM.

## Windows

Новые имена проверяются на зарезервированные символы, имена устройств и завершающие точку/пробел. Unicode и исходное написание сохраняются. Переименование только регистра использует промежуточный путь, отражённый в журнале. Проверки на Linux не заменяют native Windows smoke; поддержка Windows всей программы не заявляется этим изменением.

## Удаление из интерфейса

`POST /api/notes/delete` принимает `id` и `storageId`, возвращает 204.
Операция ставит `deleted_at` в `note_catalog` и не удаляет содержимое: файл переименовывается в
`<имя>_deleted_<uuid>.md` в той же папке, а новый путь записывается в каталог. Имя освобождается:
новую заметку можно создать с прежним именем. Записи, удалённые до этого изменения, остаются на
прежнем пути, и он занят.
Физическое `presence` продолжает отражать состояние диска; публичный descriptor
показывает `deleted`. Индекс, подсказки ссылок, граф и агентский контекст не раскрывают
содержимое скрытой заметки. Старые ссылки сохраняют идентичность и показывают заглушку.
Повторное удаление безопасно; путь записи, удалённой по-старому, не допускает создания или переноса поверх файла.
Отметка сохраняется в БД приложения, а не в YAML. Перенос папки сохраняет отметки её заметок.

Создание в UI принимает имя, а папка берётся из текущего выбора. Drag-and-drop
использует существующий rename API с `target`, UUID и ревизией каталога.
